# 2.1 — Component inventory & API-maturity classification

Task 2.1 of `upgrade-theme-quality-maturity`. Inventory of every public export of
`components/` (verified against `components/index.ts`, not README prose), each
classified as `simple-props` | `slots` | `composition-only` per design.md D1.

**No source files were modified by this task.**

## Definitions used (design.md D1)

- **`slots`** — the component renders an internal part of its own (a gauge
  track/needle, a threshold marker, a card header, a row's action button, a row
  renderer) that a consumer would realistically want to replace or restyle
  wholesale. Candidate for the MUI-convention `slots`/`slotProps` API.
- **`simple-props`** — customization is fully served by props (values, labels,
  flags, tones). Any ReactNode inputs are content, not structural parts; nothing
  is locked inside the component.
- **`composition-only`** — the component's primary body is consumer-composed
  (children / named regions the consumer fills); it is a layout/container
  primitive, not a self-contained rendering.

Non-component exports (utilities, types) are listed separately — the three-way
class does not apply to them.

## Ambiguities (flagged, not silently resolved)

1. **`ConsoleFrame`** (`composition-only`) — its named regions (`header`, `band`,
   `sidebar`, `rail`, `footer`) look like MUI `slots` syntactically, but they are
   *required consumer content*, not internal parts the component renders and the
   consumer swaps. Classified as a container; a D2 slots refactor should
   explicitly decide whether region-level `slotProps` (styling hooks per region)
   are in scope.
2. **`DossierSheet`** (`simple-props`) — `watermark` and
   `signature.{left,right,stamp}` are prop-fed *regions*, which is structurally
   slot-like. Since every part is already reachable via props, nothing is locked
   in; but a slots refactor could formalize the signature footer. Call left open.
3. **`TaskCard`** (`slots`) — borderline with `simple-props`: `steps`/`pct` props
   cover the common case, but the embedded `StepFlow` and `SegmentBar` are
   library parts rendered internally that a consumer cannot restyle or replace.
4. **`GateRow` / `RoutineRow`** (`slots`) — the internal REVIEW / RUN buttons are
   hardcoded as to their labels and styling; `onReview`/`onRun` cover behavior
   only. If the team judges label props sufficient, these drop to
   `simple-props` — flagged rather than resolved.
5. **`Terminal`** (`slots`) — the fixed `TerminalRow` kind switch is both a
   strength (closed grammar) and a limitation (no custom row kinds). Whether it
   should become a `renderRow` slot, gain a `custom` row kind, or stay closed is
   an open call.
6. **`LineChart`** (`slots`) — classified slots because the plot routine is the
   only data ingress, but the underlying finding is a **missing `data` prop**
   (see Findings). With a `data` prop added it would arguably be
   `simple-props`.
7. **`FilterRail`** (`slots`) — same tension as `Terminal`: the dim-not-hide row
   renderer is locked; `rows` data covers the simple case only.
8. **`ModuleCard`** (`simple-props`) — uses `children` as body copy, which reads
   composition-like, but the card's structure is fully prop-driven and nothing
   is composed *of library atoms*. Could equally be argued `composition-only`.
9. **`Roster`** and **`StepFlow`** (`simple-props`) — their tile/node renderers
   are uniform internal parts; a consumer wanting richer tiles/nodes has no
   escape hatch. Listed as mild future-slot candidates only.

## Findings (recorded for later tasks, no code changed)

1. **`focusRing` is not re-exported from `components/index.ts`** — it is exported
   from `components/util.ts` (used by `inputs.tsx`) but is not part of the
   public surface declared in `index.ts`. Either export it deliberately or keep
   it internal explicitly.
2. **`LineChart` accepts no data** — its series is generated and self-appended
   internally (`charts.tsx`, `data.current` ref). Every other gauge/meter takes
   controlled values. Candidate fix in a later task: add an optional `data`
   prop (falling back to the self-driving demo), consistent with
   `SegmentedMeter`/`RadialGauge`.
3. **`TagInput` renders a stock MUI `Chip color="success"`** rather than the
   library's own `Stamp` — the strongest single `slots` candidate in the
   library, and the one place a component currently reaches past the token
   grammar for a rendered part.
4. **`MeterBar` is the only "continuous fill" meter** (per its own docstring a
   deliberate quiet counterpart to `SegmentBar`) — noted here because a
   blanket "segments are drawn objects" slots pass would misread it.
5. `GateDecisionDialog` accepts no `sx` prop (every other component does) —
   noted as an inventory inconsistency, not addressed here.
