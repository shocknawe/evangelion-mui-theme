## 1. `*Component/*Props` sweep — result: **none exist** (Task 4.2 is a no-op)

Grep sweep over `components/` and `theme/` (and, for usage evidence, `app/src/` and
`doc-site/src/`), 2026-09-02:

| Grep | Target | Hits |
| --- | --- | --- |
| `(Component\|Icon\|Root)[?]?\??:\s*(React\.)?(ComponentType\|ElementType\|Component\|JSX\.Element\|ReactNode)` | component-valued props | **0** in `components/` + `theme/`. Sole near-match: `component?: ElementType` at `components/layout.tsx:182` (`ZoneTitle`) — that is MUI's standard polymorphic `component` prop (which element to render as), **not** a paired `*Props` API. Keep as-is. |
| `\b[A-Za-z]+(Component\|Props\|SlotProps)\b\s*\??:` | paired `FooComponent`/`FooProps`/`FooSlotProps` prop names | Only `defaultProps:` inside `theme/components/*.ts` (MUI's own theme-override API, unrelated to slots). No component prop pairs with an `*Props` sibling. (`TagInputProps`, `StatusLegendProps`, … are **type names** — `interface TagInputProps` — not props named `*Props`.) |
| `render[A-Z]\|render:\|renderProps\|slots\|slotProps` | render props / slot APIs | **0** in `components/` + `theme/`. |
| `InputProps\|inputProps\|componentsProps\|ComponentsProps\|classes` | MUI pre-slot-era passthroughs | **0**. No component forwards `InputProps`/`componentsProps`, and no component has a `classes` prop yet (that is Task 3.4's new surface). |
| `\.\.\.(rest\|other\|props)` | prop forwarding at all | **0** — components currently do not even spread rest props or forward `ref`; nothing legacy to migrate through. |
| `slotProps\|slots=\|Component=\|InputProps\|render[A-Z][a-z]*=` in `app/src` + `doc-site/src` | consumer-side usage of slot-style APIs | `slotProps` appears only on **stock MUI** (`Dialog`/`Popover` `paper` slot: `app/src/pages/Landing02Page.tsx:274`, `doc-site/src/docs/chrome.tsx:196`, `doc-site/src/pages/PipelinePage.tsx:461`). No `Component=` or `slots=` on any library component. All `className=`/`classes=` consumer usage is the `nerv-live` modifier on stock MUI Buttons (see 2.3 §6). |

**Finding:** the library never had a `*Component/*Props`, render-prop, or `InputProps`-style
era — it went straight from "props + `sx` only" to this change. **Task 4.2 is a no-op**:
nothing to migrate, no deprecation window to run, and `specs/component-slot-api/spec.md`'s
"Migration off `*Component/*Props` APIs" requirement is satisfied vacuously (record the
negative result in the 4.2 checkbox rather than opening code).

## 2. Slot-candidate adjudication (definitive list for 4.1)

Bar applied (D1): does the component render an internal part a consumer **realistically
swaps wholesale**? Styling-only needs go to `classes`; content needs go to props/children
— neither earns a slot. "The more freedom, the more bugs."

Starting set: the 12 components 2.1 classified `slots`. Result: **6 kept, 6 dropped.**

### 2.1 KEPT (6)

| Component | Slots kept | One-line rationale under D1 |
| --- | --- | --- |
| `TagInput` (`inputs.tsx`) | `tag` | The only place the library renders a stock MUI part (`Chip color="success"`, `inputs.tsx:224`) — off-grammar and the canonical swap-to-`Stamp` case; 2.1 finding 3. |
| `GateRow` (`status.tsx`) | `action` | The trailing REVIEW button is a hardcoded internal part (fixed label + styling, `status.tsx:363-381`); `onReview` covers behavior only. |
| `RoutineRow` (`status.tsx`) | `action` | Same case as `GateRow` — the RUN button (`status.tsx:619-637`) is a locked internal action button. |
| `FilterRail` (`navigation.tsx`) | `row` | The dim-not-hide logic (the component's whole reason to exist) is welded to a fixed 3-column row layout; a consumer with richer rows must fork today. Composition via `FilterChips` loses the dim behavior, so composition is not an escape hatch here. |
| `SiteHeader` (`navigation.tsx`) | `brand` | Every landing-page adopter realistically stamps their own lockup; `name`/`version` props only re-skin the library's `Brand`. |
| `RadialGauge` (`meters.tsx`) | `track`, `readout` | The gauge track/needle pair is D1's own named example ("gauge track/needle"); the SVG arc geometry is closed (`paths` memo, `meters.tsx:141-152`) and the center readout stack is a distinct replaceable part. |

### 2.3 Borderline cases beyond the 12 (adjudicated)

- **`Roster` / `StepFlow`** (2.1 ambiguity 9) — **drop.** Tile/node renderers are the uniform
  grammar and the data props cover it; restyle goes to `classes.tile` / `classes.node` +
  `classes.connector`. Revisit only if a real consumer asks.
- **`ConsoleFrame`** (ambiguity 1) — **no slots.** Its regions are required consumer
  content, not internal parts; nothing to swap. Resolution of the "region-level styling
  hooks" question it posed: via `classes` keys (`root`, `header`, `band`, `sidebar`,
  `main`, `rail`, `footer`), **not** `slotProps` — there is no default rendering to
  replace. Flag for Task 3.4.
- **`DossierSheet`** (ambiguity 2) — **no slots.** `watermark` and `signature.*` are
  already prop-fed regions; nothing is locked in. `classes.watermark`/`classes.signature`
  for restyle.
- **`ModuleCard`** (ambiguity 8) — **no slots** (stays `simple-props` with a `children`
  body; nothing composed of library atoms).
- **`SegmentedMeter`/`ProgressMeter` segment cells, `MeterBar` fill, `HazardRating`
  cells, `LedColumn`/`SegmentBar` segments** — **no slots.** The segment cell *is* the
  control/meter's essence (2.1 finding 4's warning taken); `classes.segment` for restyle.
- **`Waveform`, `ScanLattice`, `Marquee`, `SevenSegClock`** — **no slots.** Decorative by
  design; the drawn glyph is the component's essence.
- **`ZoneTitle`'s `component?: ElementType`** — keep; it is MUI's polymorphic prop, not a
  slot, and already satisfies the "render as a heading" need.

## 3. Exact slot set per kept component

Conventions follow 2.3: `slots={{ <part>: Component }}`, `slotProps={{ <part>: props }}`,
`classes={{ <part>: string }}` merged append-only; `root` always present and always the
outermost element; slot components receive the default part's props spread **under**
`slotProps[part]` (consumer wins) and render the library default when the slot is absent.

### `TagInput` — `components/inputs.tsx`

| Slot | Default rendering today | `slots` / `slotProps` key | `classes` key |
| --- | --- | --- | --- |
| `tag` | `<Chip color="success" label={tag} onDelete={…} />` (`inputs.tsx:224`) | `slots.tag` / `slotProps.tag` → `{ label, onDelete }` + spread | `classes.tag` |

`classes` keys: `root`, `tag`, `input`. Slot contract: the resolved component receives
`{ label, onDelete }` (plus `slotProps.tag`); omitting the slot keeps the stock `Chip` so
default rendering is unchanged.

### `GateRow` — `components/status.tsx`

| Slot | Default rendering today | `slots` / `slotProps` key | `classes` key |
| --- | --- | --- | --- |
| `action` | the pending REVIEW button — red outline, hover fill (`status.tsx:363-381`) | `slots.action` / `slotProps.action` → `{ onClick }` (bound to `onReview`) + spread | `classes.action` |

`classes` keys: `root`, `id`, `title`, `leader` (dot-leader spacer), `sub`, `priority`,
`verdict`, `action`. Contract: the slot renders **only while `verdict` is null**; once a
verdict is set the derived verdict stamp renders regardless (the stamp is data-driven —
drop its slot candidate, keep `classes.verdict`). `onReview` stays the top-level prop.

### `RoutineRow` — `components/status.tsx`

| Slot | Default rendering today | `slots` / `slotProps` key | `classes` key |
| --- | --- | --- | --- |
| `action` | the RUN button (`status.tsx:619-637`) | `slots.action` / `slotProps.action` → `{ onClick }` (bound to `onRun`) + spread | `classes.action` |

`classes` keys: `root`, `id`, `name`, `kind`, `status`, `action`. `onRun` stays top-level.
Identical shape to `GateRow` — implement the two together.

### `FilterRail` — `components/navigation.tsx`

| Slot | Default rendering today | `slots` / `slotProps` key | `classes` key |
| --- | --- | --- | --- |
| `row` | the fixed 3-column row (`id · name · kind`, `navigation.tsx:104-129`) | `slots.row` / `slotProps.row` → `{ row: FilterRow, dim: boolean }` + spread | `classes.row` |

`classes` keys: `root`, `chips` (the embedded `FilterChips`), `row`. **Dim state must not
be a `classes` key** (2.3 §6: state is not a slot class) — expose it as a `data-dim`
attribute on the row element so consumers target `[data-dim='true']`; the library default
keeps applying `opacity`/`grayscale`. The embedded `FilterChips` is deliberately **not** a
slot (compose `FilterChips` + own rows instead).

### `SiteHeader` — `components/navigation.tsx`

| Slot | Default rendering today | `slots` / `slotProps` key | `classes` key |
| --- | --- | --- | --- |
| `brand` | `<Brand name={name} version={version} />` (`navigation.tsx:357`) | `slots.brand` / `slotProps.brand` → `{ name, version }` + spread | `classes.brand` |

`classes` keys: `root`, `container` (the max-width inner bar), `brand`, `nav`, `link`,
`actions`. **`actions` stays a content prop** — it is already a ReactNode region
(consumed at `app/src/pages/Landing01Page.tsx:117`, `doc-site/src/docs/chrome.tsx:56`);
slotting it would rename an existing API for no gain. Nav links stay data-driven
(`links` prop) — dropped slot candidate.

### `RadialGauge` — `components/meters.tsx`

| Slot | Default rendering today | `slots` / `slotProps` key | `classes` key |
| --- | --- | --- | --- |
| `track` | the `<svg>` with the segmented arc `<path>`s (`meters.tsx:157-161`) | `slots.track` / `slotProps.track` → spread onto the rendered element | `classes.track` |
| `readout` | the centered `{pct}%` + `label` stack (`meters.tsx:162-169`) | `slots.readout` / `slotProps.readout` → `{ value, label }` + spread | `classes.readout`, `classes.readoutValue`, `classes.readoutLabel` |

`classes` keys: `root`, `track`, `readout`, `readoutValue`, `readoutLabel` (multi-word
parts camelCase per 2.3 §2). The `paths` memo and `lit` math stay internal — the slot
replaces the *rendering*, not the geometry calculation; a consumer supplying `track`
owns the whole SVG. `label` prop stays.

## 4. D1 judgment calls downstream tasks should know

1. **2.1's `slots` classification is revised for 6 components.** `TaskCard`,
   `GateDecisionDialog`, `SegmentedMeter`, `ProgressMeter`, `Terminal`, `LineChart` are
   adjudicated **simple-props** here (with the prop additions listed in §2.2). 2.1's
   tables stand as the inventory; this note is the API-decision record. New summary:
   **6 slot components**, 49 simple-props, 4 composition-only (of 59).
2. **`GateDecisionDialog` label props over a slot** is the main reversal. Justification:
   `GateDecision` is a closed 3-value union, the sibling `ApprovalBar` already uses
   `approveLabel`/`denyLabel`, and "extend the rail" has no realistic consumer. While in
   that file, also give it an `sx` prop (2.1 finding 5) — the only component without one.
3. **`LineChart`'s real fix is a `data` prop** (2.1 finding 2), not a slot. Recommend
   landing `data?: number[]` (self-driving demo fallback) in 4.1 alongside the slot work,
   or as its own small task — it is the only "slot" candidate that was actually a bug.
4. **`Terminal` custom rendering is a data-union extension** (`{ k: 'custom'; node }`),
   not a slot — keeps the closed grammar while adding an escape hatch.
5. **State styling is never a slot or a `classes` key.** `FilterRail`'s `dim` and any
   future state go through a `data-*` attribute or the lowercase-kebab `nerv-*` modifier
   grammar (2.3 §6).
6. **`classes` scope reminder for 3.4:** the keys listed in §3 are the *named-part* keys
   that ship with the slot work; every public component still gets `root` regardless
   (2.3 §1). `ConsoleFrame`'s region keys (§2.3) are the one `composition-only` component
   where `classes` keys are warranted without any slot.
7. **`nerv-live` is untouched** by all of this (2.3 §6).

## 5. Implementation-order recommendation for Task 4.1

1. **Shared utility first (new, in `components/util.ts`):** a small typed helper that
   resolves one slot — roughly `resolveSlot(slot, Default, slotProps, defaultProps)` —
   returning the component + merged props with the precedence *consumer slot >
   default part*, and `slotProps` spread over the defaults. Implement it once and reuse it
   in all six components so the semantics cannot drift; pair it with the `classes` merge
   order from 2.3 §5 (generated → `classes.*` → `className`) since every slot touch also
   adds `classes` and rest-prop/ref forwarding (Tasks 3.4/3.5 dependencies).
2. **`TagInput` first** — smallest diff, highest value (removes the only stock-MUI part
   from the library), fully isolated.
3. **`GateRow` + `RoutineRow` together** — identical `action` slot shape, one PR, one test
   pattern; also the pattern the other trailing-affordance components will copy.
4. **`FilterRail`** — its `row` slot needs the `data-dim` state decision (§4.5) written
   down as it lands.
5. **`SiteHeader`** — `brand` slot plus `classes` for the container/nav/link parts.
6. **`RadialGauge` last** — the only slot that touches SVG geometry; needs the closest
   screenshot check (`app/src/sections/DataDisplay.tsx`, `Landing01Page`,
   `Dashboard03Page` all render it).
7. **Bundle the non-slot prop additions** (§2.2) with the component they touch, since the
   file is open anyway: `GateDecisionDialog` labels + `sx`, `SegmentedMeter` `limitLabel`,
   `LineChart` `data`, `Terminal` `custom` row kind. All are additive and non-breaking.
8. **Verify** per CLAUDE.md: screenshot each touched component in `app/` before/after,
   exercise the slot interaction once, check the console; then run the 3.6 API-test pass
   (unknown `classes` keys ignored, `classes.root` appends, default rendering unchanged
   with no slot supplied).
