## 1. The `classes` prop contract

Every **public** component (everything exported from `components/index.ts`) accepts:

```ts
classes?: Partial<Record<SlotName, string>>
```

- **`root` is always present and always the outermost element.** `classes={{ root: 'x' }}` must be valid on every public component, even a single-part one (`Stamp`, `Stat`, `Monogram`).
- **Keys are stable, camelCase slot names** matching the component's internal parts: `root`, plus named parts where D1 says a slot is warranted (`track`, `needle`, `header`, `leading`, `trailing`, `bar`, `segment`, …). Keys are part of the public API — once shipped they do not rename.
- **Type is `Partial`** — consumers override only the parts they touch; absent keys fall back to the library default styling for that part.
- **Merge semantics: append, never replace.** A supplied class is *added to* the element's existing class list, not substituted for it: `className={clsx(nervClasses[part], classes?.[part], className)}`. Library defaults keep applying; the consumer class layers on top and wins by the specificity rule in §4.
- **`className` prop stays independent** and is applied to the root element alongside `classes.root` (root receives, in order: generated `Nerv*` class → `classes.root` → consumer `className`). Non-root parts receive only their generated class + `classes[part]`.
- Components that do not yet forward props must also spread rest props and forward `ref` to root (Tasks 3.4/3.5 territory; noted here so the merge order is implemented once, correctly).

## 2. Class-name shape (the decision)

**Exact shape: `Nerv<ComponentName>-<part>`** — PascalCase component name, single hyphen, camelCase part.

- `NervStamp-root`, `NervGaugeCard-root`, `NervGaugeCard-track`, `NervGaugeCard-needle`
- `NervStepFlow-root`, `NervStepFlow-step`, `NervStepFlow-stepActive`
- `NervTerminal-root`, `NervTerminal-line`
- `NervConsoleFrame-root`, `NervConsoleFrame-header`
- `NervChipRadioGroup-root`, `NervChipRadioGroup-option`, `NervChipRadioGroup-optionSelected`

Rules: one component, one `Nerv<ComponentName>` prefix (no per-variant suffixes — variant state is expressed via `theme` variants and `data-*`/state classes, not extra class names); parts are lowercase-first camelCase after the hyphen; multi-word parts stay camelCase, never kebab (`-stepActive`, not `-step-active`).

These names are introduced by Task 3.4. **No three `Nerv<Name>-<part>` names exist in the repo today** — the grep above is the proof; do not go looking for a precedent that isn't there.

## 3. Why NOT `MuiXyz-root`

- `Mui*` is MUI's own global class namespace for stock components (`MuiButton-root`, `MuiPaper-root`). Emitting `MuiStamp-root` for a non-MUI component **collides in the same CSS namespace** consumers already use for stock overrides, and reads as a stock component it is not.
- A consumer overriding `MuiPaper-root` in their theme would unintentionally match our components' classes (and vice versa once `cssVariables`/global selectors are in play).
- Our names are unambiguous, greppable (`grep -r "Nerv"` finds every extension point), and self-documenting as "this class belongs to the NERV library."
- Rejected alternative recorded in design.md D2: `MuiXyz-root` shape — rejected to avoid ambiguity with stock MUI components. Note the theme's own `styleOverrides` keys legitimately remain `MuiButton`, `MuiPaper`, etc. (that is how MUI's `Components<Theme>` API works); the ban applies only to classes **our components emit**.

## 4. Specificity rule (normative for Task 3.5)

- **Every override selector is a single class. No descendant nesting beyond one class.**
  - Allowed: `.NervStamp-root`, `.NervGaugeCard-track`, `&.Mui-disabled`, `&.Mui-selected`, `&[aria-pressed="true"]`, pseudo-classes/attributes on the same element.
  - Banned: `.NervConsoleFrame-root .NervTerminal-root`, `.NervStepFlow-root > div:nth-child(2)`, any compound of two `Nerv*` classes, any `!important`.
- Rationale: a consumer's `classes.root`, `sx`, or theme override must win without escalating specificity or reaching for `!important`. Because our selectors carry exactly one class of specificity, the consumer's own class (applied later on the same element, or a same-specificity later-defined rule) takes precedence naturally.
- Corollary for 3.5: styling an *inner* part goes through that part's own class, never through a descendant selector off the root. Existing theme overrides that reach across slots (`'& .MuiButtonGroup-grouped:not(:last-of-type)'` in `theme/components/buttons.ts`) are grandfathered MUI-slot selectors — migrate only where they target our own components' internals.
- This is the "flat specificity" half of D2; it is *recorded here*, implemented in 3.5.

## 5. Merge order and implementation notes for 3.4

Root class list, in order (later wins by cascade, not specificity):

1. `Nerv<ComponentName>-root` (generated, always present)
2. `classes.root` (consumer)
3. consumer `className`

Inner part: `Nerv<ComponentName>-<part>` then `classes[part]`. Use a `clsx`-style join (or template-literal join with the same semantics) — never overwrite. Tests in Task 3.6 assert: root class always present; `classes.root` appended not replacing; unknown `classes` keys ignored; `className` lands on root.

## 6. Relationship to the existing `nerv-live` modifier

`nerv-live` predates this change and stays exactly as-is: lowercase, kebab, applied by the consumer via `className`, matched in `theme/components/buttons.ts` as `'&.nerv-live'` (single-class, already compliant with §4). It is a **state/modifier class**, not a slot class — it never appears in any component's `classes` type. Future state classes, if any, follow the same lowercase-kebab `nerv-*` modifier grammar and stay out of the `classes` prop.
