# 3.1 — Children-first composition audit

Task 3.1 of `upgrade-theme-quality-maturity`. Audit of every public component in
`components/` against `specs/component-api-conventions/spec.md` D1 ("children as
the primary composition method … explicit props only where child order cannot be
permuted").

**No source files were modified by this task. No call sites were updated.**
Every component was read in full (all 13 `.tsx` files + `index.ts`), each
content-bearing prop was classified, and the decision is recorded below.

## Method: the permutability test

For each named prop that carries consumer content (`ReactNode` / string), the
question asked was:

> Could a consumer plausibly render this content in a different position relative
> to the component's other content, and would the component still make sense?

- **Yes** → the prop is a conversion candidate (children-first required). None
  survived this test.
- **No** — the prop is pinned to a fixed anchor (a header line, a footer row, a
  grid area, a nested sub-line, a corner caption, or a state that replaces
  another) → `prop-is-correct`.
- Props carrying *data* (values, labels, arrays of uniform items) are a third
  case: order is carried by the data itself (`items={…}`, `rows={…}`), not by
  named props, so the requirement's "explicit props only where child order cannot
  be permuted" clause is satisfied trivially → `data-prop`.

This mirrors the exclusions called out in the task brief: simple label/value
pairs, icons/labels passed to a specific anchor, action buttons at a fixed
corner, and `label`/`value` on a `Stat` are not conversions. **Over-conversion
would churn 40+ components and break every call site in `app/` + `doc-site/` for
zero gain** — the composition components (where children matter) already use
`children`.

## Summary

| Decision | Count | Meaning |
| --- | --- | --- |
| `already-children` | 10 | Primary consumer body already arrives via `children`. |
| `prop-is-correct` | 26 | Content props, but each sits at a fixed anchor — order cannot be permuted. |
| `data-prop` | 23 | Content is an array/record of uniform items; order lives in the data. |
| **Components audited** | **59** | Matches the 2.1 inventory count. |

**Conversions: 0.** The library already conforms to D1. Where composition exists,
`children` is the API; where named content props exist, each one is anchored to a
position the consumer cannot meaningfully move.

## Near-misses explicitly considered and rejected

1. **`GaugeCard` → all-children card** — its five regions read slot-like, but
   each is a fixed anchor (captions above/below the gauge). Children already
   carry the only permutable region (the gauge itself).
2. **`TelemetryCard.foot: [left, right]` → children/slots** — the tuple is a
   `space-between` pair; position is the meaning. Splitting it into `footLeft`/
   `footRight` props would be churn with no composition gain.
3. **`DossierSheet.signature.{left,right,stamp}` → children** — a fixed
   three-part ruled footer; a consumer would never reorder a signature line.
4. **`SectionDivider` → children** — `index`/`jp`/`title` are the numbered
   grammar itself (chip → kanji → title → rule); freeform children would break
   the "number a sequence only when it is one" rule the component encodes.
5. **`ConsoleFrame` → children-only** — impossible without losing the grid-area
   mapping (see table). Its named regions are the "child order cannot be
   permuted" allowance in its purest form.
6. **`Stat`/`StatTile` → `children` value** — named in the brief as a
   non-conversion (data props).
7. **`YesNoGate` → children responses** — the two responses are mutually
   exclusive states of one `aria-live` line, not siblings.
