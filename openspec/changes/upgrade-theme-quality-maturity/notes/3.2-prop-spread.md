**Task:** 3.2 · **Feeds:** 3.3 (`ref` forwarding), 3.4 (`classes` prop), 3.6 (API tests)
**Authority:** `specs/component-api-conventions/spec.md` — "WHEN a component receives a prop it
does not declare, THEN the component SHALL spread that prop to its root element."
**Status:** IMPLEMENTED — all 59 public components in `components/` now spread undeclared props
to their root element.

---

## 1. Convention adopted (shared helper)

Added one type to `components/util.ts` (exported from the module, not from `index.ts` — it is an
implementation vocabulary, like `focusRing`):

```ts
export type RootHTMLAttributes<Tag extends keyof HTMLElementTagNameMap = 'div'> = Omit<
  ComponentPropsWithoutRef<Tag>,
  'children'
>;
```

Every component's props interface now extends it (plus per-component `Omit`s, §3), and the
function destructures `...rest` and spreads it onto its root element:

```ts
interface StampProps extends RootHTMLAttributes<'span'> { … }
export function Stamp({ children, tone, sx, ...rest }: StampProps) {
  return <Box component="span" {...rest} sx={…}>…
```

**Rules applied uniformly:**

1. **`children` is always omitted from the rest type.** Components declare it explicitly when
   they take it; nobody gains an accidental `children` API (Task 3.1's contract).
2. **`children`-only rest typing, not `BoxProps`** — so `sx` is *not* in the rest type. Every
   component already declares `sx` and merges it into its own `sx` array; `GateDecisionDialog`
   takes no `sx` (2.1 inventory Finding 5) and was left without one (that is 3.4 territory).
3. **Rest spread goes last on the root element** (after the component's own `component`, `type`,
   `role`, `aria-label`, `onClick`, `href`), so a consumer prop wins where names collide. This is
   the deliberate semantic: an explicit consumer `aria-label` overrides a library default
   (the normal a11y-override direction), and `data-*`/`className`/`style` have no internal
   competitor. Consequence worth recording for 3.4: on the handful of roots that carry internal
   behavior (`HazardPrompt` trigger, `AgentCard`/`ModuleCard` select), a consumer-supplied
   `onClick` replaces the internal one rather than chaining — the library does not compose
   handlers. Internal handlers on *inner* elements (Roster tiles, ConsoleNav buttons, GateRow
   REVIEW, RoutineRow RUN, TagInput input, SiteHeader links) are untouched by the root spread.
4. **Merge order vs 2.3:** the root element now receives consumer `className`/`style` naturally
   through this spread; 3.4 inserts the generated `Nerv*-root` + `classes.root` ahead of it.

## 3. Why those `Omit`s exist

Any key a props interface declares that also exists on the root element's native attribute set is
destructured out of props before the spread — so it would be silently *captured* and never reach
the DOM if it stayed in the rest type. Omitting it makes that a compile error instead of a
swallowed prop:

- **`value` / `onChange`** — controlled-selection props on `ChipRadioGroup`, `NumberStepper`,
  `HazardRating`, `TagInput`, `FilterChips`, `FilterRail`, `ConsoleNav`. DOM `onChange` has an
  incompatible signature (`FormEventHandler`), and a consumer `value` would be eaten.
- **`id`** — display ids on `TaskCard`, `GateRow`, `RecallNote`, `RoutineRow`, `MemoryRow`
  (`GATE·04`, `DECISION_LOG_32`). A consumer `id` would have rendered as label text.
- **`title`** — display text on `TaskCard`, `TelemetryCard`, `RailItem`, `GateRow`, `MemoryRow`,
  `ModuleCard`, `Terminal`, `LogConsole`, `DossierSheet` (ReactNode ≠ DOM `title: string`).
- **`onSelect`** — selection callbacks on `Roster`, `AgentCard`, `ModuleCard` (DOM `onSelect` is
  a text-selection handler with a different signature).
- **`href` / `onClick`** on `WikiLink` — the component renders the anchor/button and wires these
  itself; a consumer `href` would collide with the conditional element switch.

Consumers who need the DOM attribute on those components can still get it where it is not
shadowed (e.g. `data-*`, `aria-*`), and `id`-as-DOM-id remains available on the ~40 components
that don't declare an `id` prop. Re-declaring these as distinct names (`domId` etc.) is
deliberately out of scope here.

## 4. Judgment calls

1. **`GateDecisionDialog`** — its outermost *rendered* element is MUI `Modal`'s portal root, but
   the element the component authors is the full-screen `Box` inside it; rest props land there
   (a `data-testid` is queryable, an `onClick` on the surface works). Its `aria-label="Gate
   decision required"` stays on the `Modal`; the rest type deliberately does **not** add `sx`
   (2.1 Finding 5 — left for 3.4).
2. **`WikiLink`** renders `<a>` when `href` is given and `<button>` otherwise; the rest type is
   `RootHTMLAttributes<'a'>` (the richer superset). Anchor-only attributes (`target`, `rel`) are
   therefore accepted in the button form too — acceptable for one component, and revisitable if
   3.4 splits it.
3. **Button-rooted components** (`AgentCard`, `ModuleCard`) set `type="button"` internally; a
   consumer-supplied `type` (now part of the button rest type) wins. Same for `HazardPrompt`'s
   `role`/`tabIndex`/trigger handlers — recorded in §1 rule 3.
4. **Internal `aria-label`s** (`HazardRating` "rating", `HealthColumns` "System health",
   `DigitalClock` "system clock", `HazardPrompt` from `en`, and the `ariaLabel`-prop components)
   sit *before* the spread so an explicit consumer `aria-label` wins. Verified by test — an
   earlier draft spread rest first, which let an internal `aria-label={undefined}` erase the
   consumer's attribute; the run caught it and the order was fixed.
5. **No `component`/`as`-style forwarding was added**, and no `sx`/`className` handling beyond
   what the native attribute types carry — `className` reaches the root via the spread (feeding
   2.3 §1's merge order), but generated names / `classes` are 3.4.
