# Task 3.4 — `classes` prop on every public component

Implements **Task 3.4** of `openspec/changes/upgrade-theme-quality-maturity`, following the
contract recorded in [`2.3-classes-naming-decision.md`](2.3-classes-naming-decision.md) and the
slot candidates adjudicated in [`2.2-slot-candidates.md`](2.2-slot-candidates.md).

**Scope:** 59 public components across 13 files in `components/`. Zero new dependencies. No
token / variant / design changes; when `classes` is not passed the rendered class list gains only
the generated `Nerv<ComponentName>-root` class (see "Additive-only guarantee").

---

## 1. Helper API — `components/util.ts`

Four exports, all additive:

| Export | Signature | Purpose |
| --- | --- | --- |
| `ClassesOf<Keys>` | `type ClassesOf<Keys extends string> = 'root' extends Keys ? Partial<Record<Keys, string>> : never` | The `classes` prop type. Guards the contract at compile time: a key set that omits `root` resolves to `never`, so a component cannot declare a `classes` prop without a root key. `Partial` = a consumer overrides only the parts it touches. |
| `cx` | `(...parts: Array<string \| false \| null \| undefined>) => string` | Minimal append-only `clsx` (falsy parts dropped, list only grows). |
| `nervClass` | `(component: string, part = 'root') => string` | The generated class: `Nerv<ComponentName>-<part>` (notes/2.3 §2). |
| `resolveClasses` | `<Keys extends string, Part extends Keys>(component: string, part: Part, classes: Partial<Record<Keys, string>> \| undefined, ...extra) => string` | The merge, in the recorded order (notes/2.3 §5): generated → `classes[part]` → `extra` (on the root element, the consumer `className`). |

> TS note: `resolveClasses` takes `Partial<Record<Keys, string>>` rather than
> `ClassesOf<Keys>` for its `classes` parameter because a conditional type cannot
> drive generic inference — `ClassesOf<Keys>` as a parameter made `Keys` infer
> from the `part` literal alone and collapse the parameter to `never`/`undefined`.
> `ClassesOf` remains the *props-interface* type (where the `'root' extends Keys`
> guard does its job); the helper accepts the resolved record.

## 2. Component-side pattern (uniform across all 59)

```tsx
import { type ClassesOf, resolveClasses } from './util';

export interface TelemetryCardProps extends … {
  classes?: ClassesOf<'root' | 'header' | 'foot'>;
}

export function TelemetryCard({ title, classes, className, ...rest }: TelemetryCardProps) {
  return (
    <Box {...rest} className={resolveClasses('TelemetryCard', 'root', classes, className)} …>
      <Box className={resolveClasses('TelemetryCard', 'header', classes)} …>
```

Contract points enforced everywhere:

- `classes` **and** `className` are destructured out of props *before* the `...rest` spread, so
  neither can leak to the DOM (probes assert `hasAttribute('classes')` is false).
- The root element spreads `{...rest}` *then* applies `className={resolveClasses(…, className)}`,
  so the consumer's `className` (which arrives inside `rest` for components whose root is the
  spread target) is appended **after** the generated class and `classes.root`.
- Root key is always `'root'` and always targets the outermost element — including
  `GateDecisionDialog` (the full-screen Box inside the portal, not the MUI Modal) and
  `WikiLink` (the same key on both the `<a>` and `<button>` roots).
- Part keys land only on clearly addressable elements and are kept minimal (§4 below).
- `nerv-live` and other state modifiers are never `classes` keys — they stay internal state
  classes (lowercase-kebab), per notes/2.3 §6.

## 4. Judgment calls

1. **`root`-only components** (2.2 did not enumerate parts for them): FilterChips, ConsoleNav,
   Brand, StatusLegend, StatTile, RailItem, AgentCard, RecallNote, SinkRow, ModuleCard, MemoryRow,
   AgentDot, NumberStepper, DateSegments, ZoneTitle, Monogram, Stat, GaugeCard, Stamp,
   BilingualLabel, MetadataBlock, SectionDivider, SectionHeading, FieldLabel, HazardPrompt,
   ApprovalBar, YesNoGate, BarColumnGauge, HealthColumns, LogConsole, DigitalClock, ScanLattice.
   These are atoms or single-element components; every extra key would be a public-API commitment
   with no clear addressable element. (ApprovalBar got `root` only — the approve/deny buttons are
   MUI Buttons that consumers can already reach with MUI's own classes/slots.)
2. **Keys added beyond 2.2's minimum** (each targets a genuinely addressable, restylable element):
   `MeterBar.fill`, `SevenSegClock.chip` + `SevenSegClock.countdown` (the two skins are the
   component's whole point), `LineChart.caption`, `Waveform.label` + `Waveform.caption`,
   `GateDecisionDialog.rail` (the action rail, alongside 2.2's `marker`).
3. **`FilterRail` row dim state** is expressed as a `data-dim` attribute (added in this task,
   recorded in 2.2 §3 as the intended mechanism), not a class — so consumers target
   `.NervFilterRail-row[data-dim]` for the dimmed state. Additive; when `classes` is absent and
   nothing dims, the attribute is simply absent.
4. **`SiteHeader.brand`** applies to the inner brand wrapper, while a `Brand` component dropped
   into the `name` slot keeps its own `NervBrand-root` — the two are distinguishable.
5. **`FilterRail.chips`** forwards to the embedded `FilterChips` as its consumer `className`, so
   it lands *after* `NervFilterChips-root` — a consumer can style the embedded chip row without
   wrapping it.
6. **`RadialGauge.track`** is on the `<svg>` (the only arc-bearing element); readout keys on the
   center text stack.

## 5. Additive-only guarantee

`resolveClasses` only appends. With `classes` unpassed, a root renders
`Nerv<ComponentName>-root <consumer className> <MUI's own Box classes>` — no new styles are
attached to the generated class anywhere in this task (no CSS, no sx targeting it), so the
computed styling is byte-identical to before. No token, variant, or design value changed.
