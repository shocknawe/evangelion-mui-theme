## 2. Git history — the library never had a pairing era

`git log --oneline --follow -- components/` shows 15 commits; the only API-era
commits are the `upgrade-theme-quality-maturity` sequence (3.2 prop spread, 3.3 ref
forwarding, 3.4 `classes`, 4.1 slots). Two history sweeps:

- `git log -p --all -- components/ | grep -inE '[A-Za-z]+Component\?:|ComponentProps|renderProps|InputProps|componentsProps'` → only type-name lines
  (`ComponentPropsWithoutRef<'svg'>` utility types, `TagInputProps` interface
  declarations) and the 4.1 `TagInputSlotProps` addition. No paired prop ever existed.
- `git log --all -S -E --pickaxe-regex -- components/` for
  `^\s*[A-Za-z_]+Component\?\?:\s*(React\.)?(ComponentType|ElementType)`,
  `^\s*[A-Za-z_]+Props\?\?:\s*[A-Z{]`, `renderProps`, `componentsProps`, `InputProps`,
  `render[A-Z][a-z]+\??:` → **empty** (such text has never been added or removed in any
  commit touching `components/`).

## 3. The one near-match, adjudicated

`ZoneTitle` (`components/layout.tsx:189`) accepts `component?: ElementType`
(default `'div'`) forwarded to `<Box component={component}>`. That is MUI's standard
**polymorphic `component` prop** — "render as this element" — not the `*Component`
half of a customization pairing: it takes an element name/type, carries no paired
`*Props` sibling, and its documented purpose is the document outline (WCAG 1.3.1),
not part replacement. 2.2 §1 and §2.3 reached the same verdict. Keep as-is.
