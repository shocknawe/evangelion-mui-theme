## Findings

### Finding A — blink animation never runs (`steps(1, jump-none)` in the `animation` shorthand)

- User-visible on `/`: the `FILE GATE` button is rendered with
  `className="nerv-live"` under a card captioned `BUTTON · SELECTED=BLINK
  exp-01` (`app/src/sections/Atoms.tsx:50`), but computed style is
  `animation-name: none` — it does not blink. Same for `Button variant="stamp"`
  when `.Mui-selected` / `aria-pressed="true"`.

### Fix applied (same task)

Root cause (confirmed by in-browser parser probes): Chromium rejects
`steps(1, jump-none)` for timing functions **entirely** — `jump-none` requires
n ≥ 2. It fails `CSS.supports` for both `animation-timing-function` and
`transition-timing-function`, is dropped from the `animation:` shorthand *and*
the `transition:` shorthand (`transition-duration` computes `0s`), and is
dropped as the `animation-timing-function:` longhand (`steps(2, jump-none)` and
`steps(4, jump-none)` parse in both). So interpolating
`theme.nerv.motion.snap = 'steps(1, jump-none)'` (`theme/tokens.ts:166`,
unchanged) into the `animation:` shorthand dropped the whole declaration at
every site that used it.

Fix — emit animation **longhands** instead of the shorthand, and emit the snap
through a derived, parseable value (the token itself is untouched; it is
invalid for both animation and transition timing in current Chromium, so the
helpers derive `steps(1, end)`, which parses in both contexts):

- `theme/components/util.ts` — new `snapForAnimation(theme)`:
  `motion.snap.replace('jump-none', 'end')` with rationale. `steps(1, end)` is
  the nearest parseable hard snap; because the 1 Hz keyframes hold their values
  on both sides of the 1%-wide transition window, the difference from the
  token's midpoint step is <5ms and the motion stays mechanical (no eased fade).
- `theme/components/buttons.ts:48` (`.nerv-live`) and `:88` (Button `stamp`
  selected) and `theme/components/navigation.ts:183` (StepIcon `.Mui-active`):
  `animation:` shorthand → `animationName` / `animationDuration` /
  `animationTimingFunction: snapForAnimation(theme)` / `animationIterationCount`.
- Same defect existed in the component library and on the `/` route (the 審査中
  review chip and every blink in `components/`), fixed identically:
  `components/util.ts` — new `animSnap(t)` helper; `components/chips.tsx:63`
  (Stamp), `components/clock.tsx:74` (DigitalClock colon), `components/
  terminal.tsx:118` + `:189` (Terminal cursor / LogConsole), `components/
  flow.tsx:81` (StepFlow active node), `components/status.tsx:179` (Roster
  CAUTION) + `:737` (RecallNote RETRIED), `components/feedback.tsx:182`
  (GateDecisionDialog GATE marker) + `:360` (ApprovalBar), and
  `app/src/sections/Atoms.tsx:31` (審査中 chip, inlined — the repo-root helper
  is not part of the public `@components` surface).
- `doc-site`'s `motion.step` (`steps(4, jump-none)`) is unaffected — n ≥ 2
  parses in both timing contexts (verified in-browser).
- Related latent issue (out of scope, recorded for the reviewer's Finding 2):
  `theme/index.ts:68` maps `transitions.easing.sharp` to the raw `motion.snap`
  token, and `doc-site/src/pages/foundations/MotionPage.tsx` advises
  `steps(1, jump-none)` — both inherit the same unparsable n=1 `jump-none`
  value and were not changed by this task.
- `app/src/a11y/reduced-motion.test.tsx` — the Task 6.3 inventory scanner
  matched `\banimation\s*:` only; the longhands are now covered by
  `\banimation(?:Name|TimingFunction|Duration|IterationCount)?\s*:` so the
  fail-closed inventory is unchanged (same 26 components).
