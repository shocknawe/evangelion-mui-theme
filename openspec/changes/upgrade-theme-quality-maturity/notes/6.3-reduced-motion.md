# 6.3 — reduced-motion final/static-state verification

Task 6.3 of `upgrade-theme-quality-maturity`. Adds deterministic
`prefers-reduced-motion: reduce` coverage for every animated public component,
using the `app/` Vitest/jsdom accessibility harness from Tasks 6.1 and 6.2.

Result: **26 / 26 animated public components covered** (25 components with
direct motion mechanics plus `TaskCard`, which composes `StepFlow`). The focused
suite passes **15 / 15 tests**; the complete accessibility suite passes **38 /
38 tests**. The app and package typechecks pass.

## Exhaustive inventory rule

`app/src/a11y/reduced-motion.test.tsx` scans every exported function in
`components/*.tsx` for the repository's direct motion mechanics:

- `useReducedMotion`
- CSS `animation` and `transition`
- `setInterval`, `setTimeout`, and `requestAnimationFrame`
- the reduced/normal smooth-scroll branch

The discovered names must equal the checked-in 25-component direct inventory.
Adding a new direct motion path without a named Task 6.3 path therefore fails
the suite. `TaskCard` is a separately asserted composition case because it owns
an animated `StepFlow` without repeating the motion syntax in its own function.

## Production defect fixed

The inventory found one JavaScript animation that the global CSS guard could
not stop: `HazardPrompt` set a transient `filter: invert(1)` state and cleared
it with `setTimeout`, regardless of the media preference. The component now
uses the existing `useReducedMotion` hook. In reduced mode it still invokes
`onDecide` but renders the final non-inverted state immediately and schedules no
timer. A preference change during a flash also clears the timer and settles the
state. A paired regression check proves normal motion still inverts for the
token duration and then settles, so its timing and visuals are unchanged.

No token values, variants, visual identity, or other production behavior were
changed.
